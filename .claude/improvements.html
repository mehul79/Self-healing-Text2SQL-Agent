Accuracy Improvements and Caching

What we plan to change in the LangGraph graph and the wider system to raise accuracy, and how caching works in the project today.

1. Where we are

Spider dev, execution accuracy, 1,034 questions.

The DeepSeek score predates the validator fix and was run at temperature 0.2, so a re-run at temperature 0 is the clean baseline.

The measured weakness

The biggest gap is wrong-but-valid SQL: the query runs, returns the wrong rows, and the repair loop never sees it because nothing failed. Repair only fixes queries that error. For Llama, 96 questions needed repair and 88 of those were unknown columns. 50 recovered to SQL that runs, but only about 18 returned the right rows.

2. Planned improvements

Ordered from cheapest to most work. Measure each change on the same run (first attempts against final answers), never across separate runs. Thresholds and rules come from Spider's train set, never from dev results.

Step 0. Clean baseline

  • Done. Set TEMPERATURE=0 for benchmark runs so scores stop drifting by about 0.5 points. Done in .env.
  • Done. Re-run the model with the fixed validator, which no longer rejects read-only INTERSECT, UNION and EXCEPT. The Gemma 3 12B run (77.0) used it and is the new baseline.

Step 2. Attack wrong-but-valid SQL (the biggest gap)

  • Agreement voting. Generate 3 to 5 candidate queries, run them, and pick the answer most candidates agree on, with a confidence score. Stop early when the first candidates agree. This needs a temperature above 0 or two different prompts, so the candidates differ.
  • Result sanity checks. A new verify_result node after execute_sql. It looks for empty results, NULL-only columns, and row counts that look wrong for the question. Watch for false alarms on Spider questions with ties.
  • Measure the verifier first on gold SQL and on existing results.jsonl predictions. Tune thresholds on train, never on dev.
  • Back-translation (turn the SQL back into a question and compare), only if voting leaves a clear gap.
  • Rules learned from failures on Spider's train set, added to every prompt (the approach in the ZAS-SQL paper).

Step 3. Graph shape

Today the graph is: understand, retrieve_schema, generate_sql, validate, execute_sql, then respond, with a diagnose_error and repair_sql loop capped at 3 attempts.

  • A Response Validator after execution that can send a bad result back to repair, instead of only catching errors.
  • An intent classifier that exits early on questions that are not SQL questions.
  • Optional: re-plan on failure instead of patching the same SQL.
  • The security rule stays: any new tool or node that runs a query still goes through sql_guard. The LLM is never the security boundary.

Step 4. Chat app

  • Improve respond. Today it only says "Query returned N rows".
  • A tool-calling agent (get_schema, get_sample_values, run_query, ask_clarification). Do this last, since it does not target the measured failure.

Step 5. Evaluation and models

  • Test-suite accuracy (about 1 GB download), then the BIRD benchmark. BIRD is harder: dirty values, outside knowledge, and an efficiency score. Run it after Spider shows the pipeline improving.
  • Model choice: avoid reasoning models. deepseek-v4.1-flash took 82 seconds per question and wrote about 2,000 tokens for a one-line answer. Cheap non-reasoning models (for example google/gemma-3-12b-it) are the next candidates.
  • A Postgres run, as a separate test of the Postgres path.

3. How caching works in the project today

Short answer: there is almost no caching. The project has no cache for LLM answers, schemas or query results. What exists is listed below, and it is mostly connection reuse.
WhatWhereWhat it does
Connection poolbackend/database/connection.py:19create_engine(readonly_url, pool_size=5) keeps 5 Postgres connections open and reuses them. This saves connection setup time, not LLM or query work.
Engine per database filebackend/eval/graph.py:61 (@lru_cache on engine_for)Benchmark only. One SQLite engine per Spider database is created once and reused by every question on that database.
Resume filebackend/eval/run_spider.py (results.jsonl)Benchmark only. Finished questions are saved as they complete, and a re-run skips them. It acts like a cache for paid LLM calls, keyed by question index, but it is not safe across changes. If you change the model, prompt or temperature, you must use a new --name, or the old answers will be reused.
Query storebackend/api/routers/query.py:24 (_STORE)A plain in-memory dict of past responses by query_id, so a result can be fetched again. It is a store, not a cache: it is never used to skip work, and it is lost on restart.
Streaming headersquery.py:20Cache-Control: no-cache, no-transform on the stream. This tells proxies not to cache or compress the live event stream.

What is not cached (and costs you on every request)

  • The schema is re-read on every question. retrieve_schema in backend/graph/nodes.py calls reflect_schema() each time, which queries the database catalog. The benchmark now uses the same shared reflect_schema and also re-reads the schema per question.
  • No LLM response cache. The same question at temperature 0 pays for a fresh call every time.
  • No result cache. Identical SQL is executed again each time.

Caching we could add, and when it is worth it

CacheKeyBenefitRisk
Schema cachedatabase nameRemoves a catalog read per question. Easiest win, and the prompt text stays identical.Stale after a schema change. Needs a time limit or a manual clear.
LLM response cachemodel, temperature, full prompt textFree repeat runs and cheaper benchmark re-runs.Only valid at temperature 0. It would hide model changes and defeat voting, which needs varied candidates. Must include the model and prompt in the key.
Provider prompt cachinghandled by the providerThe schema is the long, repeated part of every prompt. Some providers discount repeated prefixes automatically if the schema comes first and stays byte-identical.None to build, but richer schemas must stay stable between calls to benefit.
Query result cachenormalized SQL, databaseSkips re-running identical queries.Stale data. Skip it unless queries get slow.
Security rule for any cache: a cached SQL string must still pass sql_guard before it is executed. Do not let a cache bypass validation.

None of these caches raise accuracy. They cut cost and latency, which matters most for repeated benchmark runs and for voting, where the same prompt is sent several times. I would add the schema cache first and the rest only when a measured cost justifies it.
