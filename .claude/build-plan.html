Build plan · 6 days

Six Days to a Self-Healing SQL Agent

A day-by-day route from an empty folder to a working agent that writes SQL, runs it against a read-only database, notices when it was wrong, and repairs itself — with a React front end that streams the whole thing as it happens. The build order is chosen so each day teaches one unfamiliar thing at a time.

Python · FastAPI · LangGraph SQLAlchemy · PostgreSQL React · TypeScript · SSE ~7 hrs/day Notebook first, then module
DAY 01 Ground floor Database, ORM, packages, API. One-shot question → SQL → rows.
DAY 02 The loop asyncio, then LangGraph. The one-shot becomes a graph that repairs itself.
DAY 03 Trust & surface Validation the LLM can't talk past, plus the streaming endpoint.
DAY 04 The glass React client that renders each node as it fires, repairs included.
DAY 05 The conversation Saved chats, follow-up questions, and a live status line.
DAY 06 The scoreboard Spider dev set, scored by the official script.

02
The loop: asyncio, then LangGraph

The centre of the project. By tonight a query that fails is a query that fixes itself.

Learning goals

75 min
Done

asyncio, demonstrated rather than described

Notebook 02-async.ipynb: three fake LLM calls sequentially, then under asyncio.gather — time both. Then put a time.sleep inside a coroutine and watch the concurrency vanish. Fix it with asyncio.to_thread.

learn — the event loop is cooperative; one blocking call stalls everything. This is the bug you will otherwise ship on day three.

45 min
Done

Make the stack actually async

Switch to the async LLM client. SQLAlchemy's sync driver stays, wrapped in to_thread so DB work leaves the loop free — noting the async-engine alternative without taking that detour today.

backend/api/routers/query.py: query() is now async def, uses structured_llm.ainvoke; DB execute pulled into a sync run_query() helper and both it and reflect_schema() run via asyncio.to_thread.

learn — where async def in FastAPI helps, and where it's a lie you tell the framework.

60 min
Done

LangGraph, smallest possible version

Notebook 03-langgraph.ipynb: a TypedDict state, two nodes that each return a partial state update, one edge. Compile it. Print graph.get_graph().draw_ascii() before running anything.

learn — nodes are functions of state returning state deltas; the graph is data you can inspect, which is the entire reason to prefer it over a while loop.

70 min
Done

Port the pipeline into nodes

Define SQLAgentState (question, schema, sql, errors, attempts, result, answer). Rebuild yesterday's straight line as: understand → retrieve schema → generate → execute → respond. Still linear, same output as day one — the shape changed, the behaviour didn't.

learn — a typed shared state as the contract between nodes; why every node stays independently callable.

90 min
The differentiator Done

Conditional edges and the repair cycle

Add validate, diagnose_error and repair_sql. Route with a conditional edge: valid SQL goes to execution; a failure carries question, SQL, database error and schema into diagnosis, and the repaired query re-enters validation from the top. Bound it with MAX_REPAIR_ATTEMPTS = 3 and a terminal failure state that says what went wrong instead of inventing an answer.

learn — cycles in a graph, the conditional-edge router as a plain function, and why the bound is load-bearing rather than defensive.

backend/graph/build.py / nodes.py, matching the spec fully now: diagnose_error classifies the failure (unknown_table, unknown_column, syntax_error, permission_denied, disallowed_operation) and repair_sql injects a category-specific hint into the fix prompt instead of just the raw DB error.

45 min
Done

Break it on purpose

Feed the graph a prompt likely to make the model guess the plural, common-convention table name instead of Chinook's real singular one. Watch relation "customers" does not exist come back, get diagnosed, get repaired into customer, and succeed on attempt two. Save the rendered graph into the repo as the artefact of the day.

why — a self-healing system you've never seen heal is a claim, not a feature.

Just asking the model to guess the plural table name no longer reliably breaks it — current models default back to the schema. build.py's self-check now forces the literal query SELECT first_name, last_name FROM customers;, which still fails the same way (unknown table: customers) and still exercises the real repair path: validate fails → diagnose_error tags it unknown_table → repair_sql fixes it to customer → succeeds on attempt two. Diagram + run log saved to backend/graph/graph.ascii.txt.

End of day 2 — checkpoint

✓ Complete. The repair loop works end to end, is wired into the API, classifies failures before repairing, and has a committed diagram plus a real run showing a repair happen.

03
Trust, then the surface it streams through

Half hardening, half API design. Everything today is testable without an LLM in the loop.

Learning goals
02 full API surface 04 async generators 05 streaming graph events
75 min
Done

Three layers of validation, none of them a prompt

Parse with sqlglot for syntax. Walk the parsed tree for table and column names, checking each against the reflected schema — this is what stops hallucinated columns reaching the database. Then the allowlist: SELECT and WITH … SELECT pass, everything else is rejected by default.

learn — static analysis of SQL as an AST rather than a string; allowlist over blocklist, because you can enumerate what's safe but never what isn't.

backend/security/sql_guard.py: sqlglot syntax parse, single-statement check, node-type allowlist, known-table check, and now a known-column check too — resolves table aliases (c.first_name → customer.first_name) and skips CTE-derived columns rather than false-flagging them. Wired into backend/graph/nodes.py's validate via a new schema_columns field on SQLAgentState. The day-4 demo pass caught a real bug here: ORDER BY/GROUP BY referencing a SELECT ... AS x alias was wrongly flagged as an unknown column — fixed, with a regression test (16 security tests total now).

50 min
Done

The adversarial test file

One test_security.py of pure functions and asserts: stacked statements, a DELETE hidden in a CTE, a comment-smuggled DROP, an UPDATE dressed as a subquery. No LLM, no database, no fixtures — just inputs and expected refusals.

learn — a trust boundary is only real once it's tested in isolation from the thing it doesn't trust.

45 min
Done

Guardrails at execution

Per-session statement_timeout, an enforced row cap, a wall-clock ceiling per request. A query that would scan everything gets cut off rather than served.

learn — timeouts and limits as the last layer, sitting under validation rather than replacing it.

backend/database/connection.py: SET statement_timeout per connection and fetchmany(MAX_ROWS). backend/graph/nodes.py's execute_sql now wraps the query in asyncio.wait_for(..., timeout=QUERY_WALL_CLOCK_SECONDS) as an application-level backstop above the DB's own timeout, and a timeout is classified into its own error_category so the repair prompt tells the model to add a LIMIT or narrow the query instead of just retrying it verbatim.

60 min
Done

The rest of the endpoints

POST /api/query returns query_id, sql, status, attempts, rows and answer. GET /api/query/{id} retrieves a finished run from a small store. Errors return structured detail, not a stack trace.

learn — response models as the API contract; exception handlers; why the client shouldn't have to parse prose.

80 min
Done

Streaming: the graph narrates itself

POST /api/query/stream over Server-Sent Events, driven by graph.astream. Each node completion becomes one event — schema_retrieved, sql_generated, validation_failed, repairing, executed. Watch it with curl -N before a front end exists.

learn — async generators end to end, and why SSE is the right size of tool here rather than WebSockets (which day four adds anyway, for the comparison).

Implemented in backend/api/routers/query.py using graph.astream(..., stream_mode="updates"), one SSE event per node. Verified live with curl -N against the same forced-bad-query prompt as day 2's artefact: validate fails → diagnose_error tags unknown_table → repair_sql fixes it → second validate passes → execute_sql returns rows → [DONE], all streamed as separate events.

End of day 3 — checkpoint

✓ Complete. Security tests, endpoints, column validation, execution guardrails, and the streaming endpoint all verified — including a live curl -N run that shows a repair happening in real time.

The self-healing timeline

When a repair happens, show it rather than hiding it: attempt one, the SQL, the database's complaint, then attempt two with the corrected SQL diffed against the first. A custom component, built by hand — this is the one view that explains the whole project to someone in five seconds.

Wired into the stream demo button, which now forces a first-attempt failure so the timeline reliably has something to show.

Follow-up questions

05-follow-ups.ipynb. SQLAgentState gets history: the last 5 turns, each with its question, final SQL, and status. generate_sql and repair_sql put it in the prompt. Result rows stay out of the prompt, same as today. Test pairs: "top 5 artists by track count" then "only rock", and "invoices in 2021" then "now compare with 2022". The graph's shape doesn't change.

format_history in nodes.py builds the block and hides a failed turn's SQL. Live run on deepseek-v4-flash-0731: "only rock" added a genre join to the artists query, "now compare with 2022" widened the date range and grouped by year, and an unrelated follow-up ignored both. 06
The scoreboard: Spider, run the official way

The agent stays as it is. Today measures it on questions we didn't write, scored by a script we didn't write.

Learning goals
04 bounded concurrency 05 runtime config vs state 06 engine per database
Why SQLite

Spider's gold SQL is SQLite SQL and its scorer runs on SQLite. Porting to Postgres would change the test, and our numbers would no longer compare to anyone else's.

30 min

Get Spider onto disk

The dev set is 1,034 questions over 20 SQLite databases. Unzip it into data/spider/, keep it out of git, and read three examples by hand: question, gold SQL, db_id.

60 min

Point the graph at any database

Nodes stop importing the global engine. The engine comes in through LangGraph's config, one per db_id, cached for the run. SQLite files open with mode=ro, so the read-only rule still holds.

learn state is what the graph reasons about. Config is what it runs on. An engine is the second kind.

45 min

Make the dialect a parameter

sql_guard takes a dialect. The prompt tells the model which one to write. statement_timeout only runs on Postgres, and the wall-clock limit covers SQLite. Chinook's self-checks must still pass.

60 min

Twenty questions in a notebook

06-spider-eval.ipynb: run 20 dev questions through the graph, write one predicted SQL per line, and read every failure. Expect the first bugs in our code, not the model.

45 min

Score it with the official script

Feed the predictions file to Spider's test-suite evaluator in execution mode. We don't grade ourselves.

60 min

Port the harness

backend/eval/run_spider.py. An asyncio.Semaphore caps parallel questions so we stay under the provider's rate limit. One JSONL line per question with attempts, status, error category, and latency. Runnable check: a 5-question slice.

45 min
The number that matters

Full dev set, twice

Run once with repairs on, and once with MAX_REPAIR_ATTEMPTS = 0. The gap between the two is what self-healing is worth, measured on 1,034 questions instead of five.

End of day 6 — checkpoint

Two execution-accuracy numbers from the official scorer, with and without repair, plus first-attempt accuracy, recovery rate, and cost per question. BIRD later reuses the same harness with a different loader.

Done, and deliberately not done

Four days bought a system that demonstrates its own thesis. It does not buy a platform — and the cut list matters as much as the build list.

Shipped
  • ✓Natural language → schema-grounded SQL
  • ✓Read-only execution, enforced at the database
  • ✓Validation independent of the model
  • ✓Automatic diagnosis and repair, bounded at three
  • ✓Inspectable LangGraph, rendered and committed
  • ✓Streaming API and a client that renders each step
  • ✓Baseline vs self-healing, measured on five questions
Cut, and when to add it
  • →pgvector schema retrieval — when the schema stops fitting in a prompt
  • →Multi-turn conversation — now day five, history from our own table instead of a checkpointer
  • →LangSmith and OpenTelemetry — when a failure gets hard to reproduce
  • →Spider / BIRD benchmarks — Spider is now day six, BIRD after it
  • →Charts and visualisation — after the table is genuinely not enough
  • →Docker, second database engine, fine-tuning — not this week

If a day runs long, the block to drop is never validation and never the repair loop. Drop the WebSocket comparison, drop shadcn, drop the ORM half of the SQLAlchemy notebook. The project's claim is that the surrounding architecture — not the model — is what makes text-to-SQL reliable, and only two days of this plan actually prove that.
